# ノウハウ実行ランナー

商材が実行されない原因は、情報が足りないことではない。
**情報と実行のあいだに「人間の気力」が挟まっていること** が原因である。

このスキルはその隙間を埋める。読ませるのではなく、動かす。

---

## 全体フロー

```
フェーズ0   棚卸し      materials/ を読み、何ができる商材かを1文で確定する
フェーズ1   手順書化    実行専用の SKILL.md に変換する（抽象論は捨てる）
フェーズ1.5 自動レビュー 人手ゼロで査読し、自分で直す（最大3周）
フェーズ2   実行        手順書どおりに実際に手を動かす
フェーズ3   自動化      繰り返す部分を定期実行に落とす
```

**セッション開始時、`work/state.md` を読んで現在フェーズを判定し、そのフェーズから即実行する。**
`work/state.md` が無ければフェーズ0から始める。ユーザーに聞かない。

---

## フェーズ0：棚卸し

### やること

1. `materials/` 配下を全部読む
   - PDF → `pdf` スキルで読む
   - 音声・動画の書き起こしテキスト → そのまま読む
   - URL のメモ → WebFetch で取得（取れなければ「取得不可」と記録して先へ進む）
   - 画像しかない場合 → Read で読み取る
2. 読んだ内容を **実行に寄与するか** で仕分ける

### 仕分けの基準

| 残す | 捨てる |
|---|---|
| 具体的な作業手順 | マインドセット・心構え・精神論 |
| 数値・基準・テンプレート | 著者の成功体験の物語 |
| 使うツール名・サービス名 | 「本気でやれば変わる」系の煽り |
| 順序の指定 | 抽象的な原則だけで手が動かないもの |

捨てたものは `work/dropped.md` に一行ずつ記録する。判断の根拠が残ればよく、丁寧に書く必要はない。

### 出力：`work/inventory.md`

```markdown
# 棚卸し

## この商材は何ができるようになるものか
（1文。「〜すると〜になる」の形で書く。書けないなら商材を読み違えている）

## 前提として必要なもの
- アカウント：
- ツール／サービス：
- お金：
- 1回あたりの所要時間：

## ステップ候補（順序つき）
1. …
2. …
3. …

## 商材に書かれていない穴
（実行するには決まっていない箇所。フェーズ1で埋めるか、ユーザーに聞く）
```

### 完了条件

- `work/inventory.md` が存在する
- 「何ができるようになるか」が **1文** で書かれている
- ステップ候補が **3つ以上** 並んでいる
- `work/state.md` のフェーズが `1` に更新されている

## フェーズ1：手順書化

商材を **読み物から実行物に変換する** 工程。ここがこのキットの核心。

### やること

`.claude/skills/<商材の短い英小文字スラッグ>/SKILL.md` を新規作成する。

例：`.claude/skills/blog-monetize/SKILL.md`

### 手順書のテンプレート

```markdown
---
name: <スラッグ>
description: <この手順書がどんな時に呼ばれるべきか。「〜したいとき」「〜を作るとき」を具体的に>
---

# <商材名>：実行手順

## ゴール
（達成された状態を1文で。「〜が〜個ある状態」のように、目で見て確認できる形にする）

## 前提
- 必要なアカウント：
- 必要なファイル：
- 人間にしかできないこと：（あれば明記。無ければ「なし」）

---

## ステップ1：<動詞で始まるタイトル>

**やること**
（具体的に。「検討する」ではなく「〇〇を5件書き出す」）

**使うもの**
（ツール／入力ファイルのパス）

**出力先**
`work/outputs/<ファイル名>`

**完了条件**
（例：`work/outputs/titles.md` に見出し案が10件、各30文字以内で存在する）

**詰まったときの代替**
（例：情報が足りなければ既存の3件で先に進み、不足を state.md に記録する）

---

## ステップ2：…
（以下同様）

---

## 禁止事項
- 公開・投稿・送信・課金・削除は行わない。`work/drafts/` に置いて停止する。
- 完了条件を満たさないままステップを閉じない。
```

### 手順書を書くときのルール

1. **1ステップ = 1回の作業で終わる粒度**にする。半日かかるステップは分割する。
2. **曖昧語を使わない。** 禁止語：「適切に」「いい感じに」「しっかり」「必要に応じて」「検討する」
   → 数・期限・ファイル名・判定基準のいずれかに置き換える。
3. **人間の判断が要る箇所は明示する。**
   「ここはユーザーに確認する」と手順書に書く。勝手に決めない。
4. **商材に書かれていない箇所は、埋めた事実を書く。**
   `> 補完：商材に記載なし。一般的な手順で補った` と手順書内に注記する。
5. **成果物のファイルパスを必ず決める。** 出力先が決まっていない手順は実行できない。

### 完了条件

- `.claude/skills/<スラッグ>/SKILL.md` が存在する
- **すべてのステップに完了条件がある**（1つでも欠けていたら未完了）
- **すべてのステップに出力先ファイルパスがある**
- 禁止語がゼロ
- `work/state.md` のフェーズが `1.5` に更新されている

## フェーズ1.5：自動レビュー（人手ゼロ）

書いた本人が読み返しても穴は見つからない。**別の文脈で読ませて指摘させる。**
ユーザーに見せてはいけない。ユーザーを挟まずに完結させる。

### 手段（上から順に試す。使えるものを1つ使えばよい）

**手段A：サブエージェント（同一セッション内・最も速い）**

Agent ツールで `general-purpose` を起動し、次を渡す：

> `.claude/skills/<スラッグ>/SKILL.md` を読んで査読してほしい。
> 下のチェックリストに照らして、**問題点だけ**を箇条書きで返すこと。
> 良い点・要約・励ましは書かないこと。問題がなければ `NO_ISSUES` の1行だけ返すこと。
> （チェックリストを貼る）

**手段B：別セッション（文脈が完全に切れるので精度が高い）**

```bash
claude -p "$(cat .claude/skills/<スラッグ>/SKILL.md)

---
上の手順書を査読して、問題点だけを箇条書きで返して。
良い点や要約は不要。問題がなければ NO_ISSUES とだけ返して。
チェックリスト：
1. 完了条件が無い、または目で確認できないステップ
2. 「適切に」「いい感じに」「しっかり」「必要に応じて」等の曖昧語
3. 出力先ファイルパスが決まっていないステップ
4. 前のステップの成果物なしに実行できないのに順序が逆になっている箇所
5. 実在しないツール・サービス・コマンドへの依存
6. 公開・投稿・送信・課金・削除を自動実行させてしまう記述
7. 1ステップの分量が大きすぎて1回で終わらないもの
8. 精神論・抽象論が手順として残っているもの"
```

**手段C：Codex など別ツール（入っていれば）**

```bash
codex exec "（同じプロンプト）"
```

### レビュー後にやること

1. 返ってきた指摘を **自分で直す**。ユーザーに転送しない。
2. 直したらもう一度レビューに掛ける。
3. **最大3周**まで。3周して残った指摘は `work/review.md` に
   「残した理由」つきで記録し、先へ進む。無限ループさせない。

### 完了条件

- レビュー結果が `NO_ISSUES`、または残指摘が `work/review.md` に理由つきで記録されている
- 指摘に対する修正が手順書に反映されている
- `work/state.md` のフェーズが `2` に更新されている

---

## フェーズ2：実行

ここからは **作った手順書に従って、実際に手を動かす。**

### やること

1. フェーズ1で作った `.claude/skills/<スラッグ>/SKILL.md` を読み込む
2. ステップ1から順に実行する
3. 各ステップ終了時に：
   - 成果物を `work/outputs/` に保存
   - **完了条件を満たしたか自分で判定する**（満たしていなければ、そのステップをやり直す）
   - `work/state.md` を更新する
4. 公開・投稿・送信に当たるものは `work/drafts/` に置いて **そこで止まる**

### 止まるべき場面

以下に当たったら、作業を止めてユーザーに1回だけ確認する：

- ユーザー本人の情報（実績・経歴・単価・連絡先）が必要で、`materials/` にも無いとき
- 課金が発生するとき
- 外部サービスへのログインが必要なとき
- 既存ファイルを上書き・削除する必要があるとき

止まるときは **何が決まれば再開できるか** を1行で示す。曖昧に「どうしますか」と聞かない。

### 完了条件

- 手順書の全ステップが完了条件を満たしている
- `work/outputs/` に成果物が存在する
- 人間の確認が要るものが `work/drafts/` に揃っている
- `work/state.md` のフェーズが `3` に更新されている

---

## フェーズ3：自動化

一度実行して終わるノウハウは少ない。**繰り返す部分だけ**を自動化する。

### やること

1. 実行した手順のうち、**同じことを繰り返す部分**を抜き出す
2. 頻度ごとに手段を選ぶ

| 頻度 | 手段 | 備考 |
|---|---|---|
| 毎日・毎週の定期 | `/schedule` | PCを閉じても動く |
| 単発で回したい | `claude -p "..."` | シェルから1回実行 |
| 条件が揃うまで繰り返す | `/loop` | セッション内で反復 |

3. 登録した内容を `work/automation.md` に記録する

### `work/automation.md` の形式

```markdown
# 自動化の登録内容

## 1. <名前>
- 手段：/schedule
- 頻度：毎週月曜 9:00
- 何をするか：
- 出力先：
- **解除方法**：（必ず書く。止め方が分からない自動化は事故になる）
```

### 自動化してよい / いけない

| してよい | してはいけない |
|---|---|
| 下書きの生成 | 投稿・公開 |
| 情報収集・集計 | 送信（メール／DM） |
| ファイルの整理・リネーム | 課金・支払い |
| レポート作成 | ファイル削除 |

### 完了条件

- `work/automation.md` に、登録内容と **解除方法** が書かれている
- 自動化対象に公開・送信・課金・削除が含まれていない
- `work/state.md` のフェーズが `完了` に更新されている

---

## `work/state.md` の形式

毎セッション、必ず更新する。次のセッションのあなたが唯一頼りにする情報。

```markdown
# 進捗

- 現在フェーズ：2
- 商材スラッグ：blog-monetize
- 最終更新：2026-07-27

## 完了したステップ
- [x] フェーズ0 棚卸し
- [x] フェーズ1 手順書化
- [x] フェーズ1.5 レビュー（2周／残指摘1件）
- [ ] フェーズ2 実行 ← ステップ3まで完了、ステップ4から再開

## ユーザーの確認待ち
- work/drafts/post-01.md（SNS投稿文。本人が投稿する）

## 次にやること
ステップ4「見出し10案の絞り込み」を実行する
```

## 複数の商材が入っていた場合

`materials/` に無関係な商材が複数あるときは、**1本ずつ順に処理する**。混ぜない。

1. `work/inventory.md` に全部を並べる
2. **いちばんステップ数が少ないもの** から着手する（早く1周終わらせて穴を見つけるため）
3. 1本が「フェーズ3 完了」まで行ってから次に移る

どれから始めるかをユーザーに聞く必要はない。上の基準で自分で決めてよい。

---

## このスキル自体が詰まったとき

- `materials/` が空 → 「商材ファイルを `materials/` に置いてください」とだけ伝えて止まる
- 商材が読めない形式（DRM付き等）→ `work/state.md` に記録し、読めた分だけで進める
- ゴールが1文で書けない → 商材が手順ではなく概念集。その旨を伝え、**それでも抽出できる作業だけ**で手順書を作る
